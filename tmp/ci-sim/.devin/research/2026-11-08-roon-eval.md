# Rune (reel said "Roon") - eval note

Source reel: ox8erlin DfeIuzRMHn5 (reels batch-6 survey,
`.devin/research/2026-11-08-reels-batch6-survey.md`). Evaluated
2026-11-08. Issue #415.

## What it is

Rune (`github.com/anomalyco/rune`, ~883 stars, created Oct 2026): native
GPU-rendered Rust UI framework by Anomaly, the team behind OpenCode.
Correction to reel: the project is named **Rune**, not "Roon".

Own stack, no webview: wgpu renderer (one instanced SDF quad pass, single
draw call), Taffy layout pinned to device pixels, Parley/HarfRust/skrifa/
fontique text, AccessKit a11y, analytic spring animations, rune-kit
component library (OpenCode UI vocabulary). Targets macOS/Windows/Linux;
web target experimental via WebGPU canvas. MIT license.

The differentiator is agent-first design: every app runs **headless** -
renders to PNG, dumps the element tree (same tree as the a11y tree),
accepts scripted mouse/keyboard input. README literally says "Give your
coding agent this repo." First big job: rebuilding the OpenCode desktop.

## Maturity / risks

- **Pre-release**: no crates.io package, no tagged releases - pinned to a
  git rev of `dev`. Maintainers don't take PRs (issues only, "our agents
  turn it around").
- Windows GPU-fallback path unanswered in community thread.
- Docs written for agents; human docs thin (HN/dev.to consensus).
- Headless verification only covers **Rune apps** - it is not a general
  "verify any app" tool.

## Bundle fit

- `extensions/computer-use` + `cu-realtime`: drive real OS apps via
  UIA/screenshots - complementary layer, not overlapping. Rune headless
  would only matter if we build UI *in* Rune.
- `extensions/rust-core` (PyO3): CPU/OS/memory work, unrelated to UI.
- ux-researcher/art-director profiles: could consume Rune's element-tree
  dumps IF a Rune surface existed.

## Recommendation

**Track, do not adopt.** Value case is real but narrow: agent-drivable UIs
are a genuinely new capability, and MIT + Rust fits the bundle. However
it is pre-release with no stable artifact, and it only pays off if a
future deliverable is a Rune app (e.g. an agent-facing dashboard). No
integration now; revisit if/when a UI surface is scoped - at that point
the headless PNG/tree/input loop is a legitimate verification path that
computer-use cannot provide for non-OS-rendered content.
